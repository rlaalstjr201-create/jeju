# ADR-0129: 문화 목록은 하루 한 벌 — 완성된 목록을 D1에 두고, 자정 직후 미리 짓는다

Status: Accepted (2026-11-18).

## 확인한 것 (운영, 11-18 00:37~01:00 KST)

- **첫 방문에 핫한 선반이 없음:** 첫 방문의 서울 홈은 24초가 넘도록 관광지 기분 선반만 보였다. 밤 놀거리·오늘 무대 같은 선반은 문화 목록이 와야 생긴다.
- **목록 응답이 느림:** `/api/culture?city=seoul`는 31초 걸렸다(89KB, KIX 엣지).
  - 목록은 엣지(데이터 센터)마다 따로 지어지고, 그 엣지에서만 자정까지 남는다(ADR-0112 6, ADR-0117 Amendment 6).
  - 짓는 일은 서울시 목록 약 20쪽과 KOPIS 공연 상세 약 200건이다.
  - 그래서 그날 엣지마다 처음 묻는 사람은 앱이 기다리는 15초를 넘긴다.
  - 같은 사람도 다른 엣지로 가면(KIX·ICN) 다시 기다린다.

## Decision

1. **완성된 목록은 D1에 둔다**(기존 `EVENTS_DB`, 표 `culture_lists`, migrations/0003)
   - 「완성」은 엣지에 자정까지 두는 목록이다. KOPIS가 중간에 끊긴 목록(10분짜리)은 넣지 않는다.
   - 엣지 캐시에 없으면 D1을 먼저 읽는다. 오늘 것이 있으면 그대로 답하고, 그 엣지도 자정까지 둔다.
   - 없을 때만 지금처럼 짓는다.
   - 키는 엣지 캐시의 키 그대로다. KOPIS 키가 있는 목록과 없는 목록이 섞이지 않는다.
   - 7일 이상 지난 줄은 쓸 때 지운다.
   - 운영 주소(yeochana.com)로 온 요청만 D1을 읽고 쓴다. 프리뷰 배포(*.pages.dev)는 같은 DB를 쓰기 때문이다.
   - D1 호출 3번(읽기·쓰기·지우기)도 무료 플랜의 호출 수(50)에 넣어 KOPIS 청크 수를 정한다.
   - D1이 없거나 실패하면 지금과 똑같이 동작한다.
2. **자정 직후 미리 짓는다**(`.github/workflows/warm-culture.yml`, 00:05 KST)
   - 공개 주소를 한 번 묻기만 한다. 비밀값도 쓰기 권한도 없다.
   - 완성되지 않았으면 11분 뒤 다시 묻는다. 최대 3번이다.
   - 실패해도 앱은 지금처럼 스스로 짓는다. 그날 처음 완성한 엣지가 D1에 넣으면 그때부터 모두 빨라진다.
3. **개인정보:** 바뀌지 않는다. D1에 들어가는 것은 서울시·KOPIS 공개 행사 자료뿐이고, 묻는 사람에 대한 것은 없다.

## Consequences

- 그날 목록이 한 번 완성되면 어느 엣지든 D1 한 번 읽기(수십 ms)로 답한다.
- D1 쓰기는 완성될 때마다 쓰기·지우기 한 번씩이다. 보통 하루 한두 번이고, 동시에 짓는 엣지가 있으면 그만큼 더 쓴다. 읽기는 엣지 캐시가 없을 때만이다. 모두 무료 한도 안이다.
- **GitHub Actions 비용:** 하루 1~2분이다. 끝까지 완성되지 않는 날은 최대 약 28분이다(요청 120초 × 3 + 기다림 11분 × 2, 작업 제한 30분).
- **남는 위험:** GitHub 러너가 닿는 엣지(미국)에서 서울시 API가 막히면 미리 짓기가 실패한다. 그날은 앱이 지금처럼 짓는다. 배포 뒤 손으로 한 번 돌려서 확인한다.
- **낮에 목록 형식을 바꾸는 배포:** 옛 코드로 지은 D1 사본이 그날 자정까지 모든 엣지에 남는다. 형식이 바뀌는 배포라면 그날 줄을 손으로 지운다.
- **배포 순서:** 운영 D1에 표를 먼저 만들고(`wrangler d1 migrations apply yeogwi-events --remote`), 그다음 함수를 배포한다. 표가 없으면 함수는 D1 없이 동작한다(읽기 실패는 null).
