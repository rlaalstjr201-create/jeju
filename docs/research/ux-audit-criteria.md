# UX/UI 감사 기준: 오늘제주 · 마이리얼트립

작성 2026-10-02. 대상: onuljeju.com 「오늘제주」, myrealtrip.com 마이리얼트립.
목적: 두 서비스를 직접 써 보고, 우리 앱(여행계획짜기 귀찮아:제주)에 가져올 것과 피할 것을 고른다.

## 0. 범위와 전제

- 보는 범위는 **놀거리·먹을거리**뿐이다. 항공·배·렌터카·숙소 화면은 점수를 매기지 않는다.
- 우리 사용자는 계획 없이 다니는 여행자(P)다. 「지금 여기서 뭐하지」 순간에 앱을 켠다(context.md, ADR-0025, ADR-0059).
- 우리 흐름: 기분 한 번 → 근처 3곳 → 카카오맵 길찾기. 로그인 없음, 가격·평점·운영시간 없음(ADR-0025, ADR-0026, ADR-0058).
- 주인 피드백: 첫 화면이 비어 보이고 덜 만든 것 같다. 카드 구조·화면 배치·시각·흐름이 당근 같은 곳보다 뒤처진다.
- 그래서 이 감사는 「점수 매기기」보다 「왜 저쪽은 꽉 차 보이는데 덜 피곤한가」를 찾는 데 쓴다.

## 1. 증거 규칙

1. 모든 점수 옆에 증거를 하나 이상 단다. 스크린숏 파일명(`shots/<서비스>-<과제>-<폭>-<번호>.png`) 또는 관찰한 사실(「홈 첫 화면에 배너 3개」).
2. 확인하지 못한 항목은 점수 칸에 `확인 못 함`이라고 쓴다. 짐작으로 3점을 주지 않는다.
3. 결제·예약 확정 화면은 들어가지 않는다. 로그인은 사용자가 크롬에서 해 둔 상태만 쓴다(감사자가 로그인하지 않음). 그 너머는 `확인 못 함`.
4. 과제 측정은 서비스·폭마다 1회다. 실패해도 다시 돌리지 않고 실패를 그대로 적는다.
5. 측정 환경을 적는다: 날짜·시각, 브라우저, 폭(390px 모바일 / 1440px 데스크톱), 위치 권한 허용 여부, 앱 설치 유도 팝업 유무.
6. 감사자 1명이면 주관 항목(시각·첫인상)은 「1인 판단」으로 표시한다.

## 2. 점수 계산

- 기준마다 1~5점. 차원 점수 = 그 차원 기준 점수의 평균.
- 총점 = Σ(차원 가중치 × 차원 점수 ÷ 5). 100점 만점.
- `확인 못 함` 기준은 평균에서 빼고, 빠진 개수를 함께 적는다.
- 점수보다 증거 문장이 더 중요하다. 제안은 점수가 아니라 관찰에서 나온다.

## 5. 고정 과제

각 서비스에서 같은 순서로 돌린다. 390px(모바일) 1회. 1440px은 T1만. 위치는 제주시청 근처로 가정하고, 위치 권한을 줄 수 없으면 「제주시」를 고른다.

| # | 과제 | 성공 조건 | 잴 것 |
|---|---|---|---|
| T1 | 처음 열고 5초 보고 「뭐 하는 곳인지」 한 문장 쓰기 | 놀거리·먹을거리 관련 문장 | 문장 원문, 첫 화면 스크린숏, 누를 수 있는 것 개수 |
| T2 | 지금 근처 먹을 곳 하나 정하기 | 가게 하나 이름을 고름 | 탭 수, 초, 입력 수, 막다른 길 수 |
| T3 | 비 오는 날 실내 놀거리 찾기 | 실내 장소 하나 고름 | 탭 수, 초, 「실내」 필터·문구 유무 |
| T4 | 장소 상세 → 길찾기 | 지도 앱/길찾기 화면 도달 | 탭 수, 초, 어느 지도로 가나 |
| T5 | 마음에 든 곳 저장 → 홈으로 갔다가 다시 찾기 | 저장한 곳 다시 열기 | 탭 수, 초, 로그인 요구 여부 |
| T6 | 「아무거나」 하나 골라 달라고 하기 | 추천 1곳이 나옴 | 그런 기능 유무, 탭 수 |
| T7 | 뒤로 가기 3번 | 직전 목록·스크롤 복원 | 복원 여부, 처음으로 튕긴 횟수 |

측정 규칙:
- 탭 수: 스크롤은 세지 않는다. 팝업 닫기는 따로 센다.
- 초: 첫 화면이 다 뜬 때부터 성공 화면까지. 화면 녹화로 잰다.
- 막다른 길: 로그인 벽, 결과 0건, 앱 설치 강요, 404.
- 3분 안에 못 하면 「실패」로 적고 멈춘다.

선택 도구(여러 명이 쓸 때만): SUS 10문항(Brooke 1996)으로 전체 사용성, UEQ-S 8문항(Schrepp 외 2017)으로 실용·감성 품질. 1인 감사에는 점수를 내지 않고 참고만 한다.

## 7. 결과 → 우리 제안

관찰 하나당 한 줄. 판정은 셋 중 하나다.

- **유지**: 우리가 이미 더 낫거나 같다. 바꾸지 않는다.
- **도입**: 저쪽이 낫고, 우리 결정과 충돌하지 않는다.
- **피함**: 저쪽이 하지만 우리 목표에 해롭다.

```
| 관찰(증거) | 판정 | 우리 화면에 적용 | 충돌 ADR | 충돌 시 처리 |
| 마리트 홈 첫 줄이 큰 사진 카드 1장 + 가로 줄 (myrealtrip-T1-390-01.png) | 도입 | 홈 기분 목록 위 사진 한 장 | SPEC §1-1(한 번에 하나) | 새 ADR 필요, 사용자 결정 |
| 카드에 별점·할인율 (…png) | 피함 | — | ADR-0025·0058(평점 없음), SPEC §14 | 해당 없음 |
```

충돌 점검 목록(도입 후보마다 확인):
- ADR-0025·0058: 카드에 가격·운영시간·평점 없음. 기분 한 번 → 3곳.
- ADR-0026: 로그인 없음. ADR-0029: 저장은 기기에만, 일정 아님.
- ADR-0067: 운전자는 길 안내만 본다. 첫 탭 한 번, 길찾기 한 탭.
- ADR-0070: 흰 바탕 + 3색, 그림자·그라데이션 없음.
- SPEC §14: 배지·칩·별점·토스트·가운데 정렬·이모지 0건.
- ADR-0074: 체험마다 확인된 예약 경로 하나.

충돌하는 도입 후보는 바로 고치지 않는다. 「기존 결정을 다시 볼 이유」로 적고, 사용자 결정 뒤 새 ADR을 낸다(CLAUDE.md 절대 룰).
