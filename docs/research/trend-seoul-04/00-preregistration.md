# 트렌드 04 — 조회 창을 넓히고 자동 후보 목록을 만들면 얼마나 잡히나 (사전등록)

작성 2026-11-04 KST, 실행 전에 커밋한다. 커밋 뒤에는 조회·추출 규칙·판정·결론 규칙을 바꾸지 않는다. 조회는 한 번이다.
실행자는 기준 목록의 항목 이름을 보지 않고 이 설계를 정했다(`01-reference.md`·`03-match.md`의 항목 표를 읽지 않음).

## 원인 진단 (01~03 원자료에서)

- 01 S3 네이버 블로그 「최신순 100건」의 글 날짜: 성수 팝업 100건이 **모두 2026-11-04**, 홍대 팝업 100건도 **모두 11-04**, 이태원 11-01~11-04.
- 02 S5 뉴스 100건: 성수 11-03~11-04, 홍대 11-02~11-04.
- 즉 01·02의 블로그·뉴스는 사실상 **하루~사흘치**만 봤다. 11-05에 열린 팝업 대부분은 그보다 앞서 소개됐을 것이므로, 29%는 조회 창이 원인일 수 있다.
  (주인 지시 2026-11-04: 「그냥 안된다고 하지만 말고 … 추론하고 연구하고 결과를 만들어내」)

## 개선 (같은 기준 목록·같은 기준일·같은 반경)

- **H1 넓게 받기:** 네이버 블로그·뉴스 검색 API, 최신순 100건씩 `start` 1~901(10쪽, 검색어당 최대 1,000건), 2026-10-08 이후 글만.
  검색어(지역별 4개, 실행자가 지명으로 정함):
  - 성수: 「성수 팝업」「성수동 팝업」「성수 팝업스토어」「연무장길 팝업」
  - 홍대: 「홍대 팝업」「홍대 팝업스토어」「연남동 팝업」「합정 팝업」
  - 이태원: 「이태원 팝업」「한남동 팝업」「한남 팝업스토어」「용산 팝업」
  호출 상한: 블로그 120회, 뉴스 120회(하루 25,000회 한도 안).
- **H2 자동 후보 목록:** H1 글 + 03의 유튜브 영상(제목·설명)에서 01과 같은 규칙(「… 팝업(스토어)」 앞 1~3어절)으로 이름 후보를 뽑아
  정규화(띄어쓰기·기호 제거)하고, **2026-10-15 이후 서로 다른 글·영상 2건 이상**에서 나온 후보만 남긴다. 지역은 그 글이 나온 검색어의 지역.
  이 목록이 「서비스에 쓸 후보」다.

## 판정 (새 Opus 하위 에이전트, 실행자·이전 판정자와 다름)

- **R1 노출 재현율:** 기준 목록 항목이 H1 글(제목·요약)이나 유튜브 영상 어딘가에 분명히 언급됐는가.
- **R2 후보 재현율:** 기준 목록 항목이 H2 후보 목록에 (같은 팝업으로 볼 수 있는 이름으로) 들어 있는가.
- 애매는 못 잡음. 이태원(2개)은 판정 제외, 따로 적음. 성수·홍대 31개 기준.
- 정밀도: H2 후보 목록에서 표본 20개를 뽑아 11-05에 실제로 반경 안에서 열렸는지(웹 확인 최대 20회).

## 미리 정한 결론 규칙 (R2 기준 — 서비스가 실제로 쓸 것은 후보 목록이므로)

- **R2 60% 이상이고 정밀도 50% 이상** → 2단계(구별 「이번 주」 목록)를 이 방식으로 만든다(사람이나 AI가 후보를 검수해 올리는 단계 포함).
- **R2 30~60%** → 작은 판(「일부만」을 밝힘)을 검토하고, 낮은 원인(R1이 낮은지 = 출처 문제, R1은 높은데 R2가 낮은지 = 추출 문제)을 다음 개선 대상으로 정한다.
- **R2 30% 미만** → 이 방식으로는 만들지 않는다. R1이 60% 이상이면 「글에는 있는데 못 뽑음」이므로 추출을 AI로 바꾸는 시험을 다음으로 한다.

## 미리 적는 예상 (틀려도 고치지 않는다)

실행자(Claude) 예상: R1 60~80%(창을 넓히면 대부분 어딘가에는 언급됨), R2 35~55%(규칙 추출은 이름이 「브랜드 팝업」 꼴이 아니면 놓침), 정밀도 30~50%.
