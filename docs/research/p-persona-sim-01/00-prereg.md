# 가상 여행자 1000명 UX 시뮬레이션 — 사전등록

작성 2026-10-08, 결과를 보기 전. 이 파일은 실행 뒤 고치지 않는다(고치면 그 사실과 이유를 끝에 덧붙인다).

## 질문

「언제」(날짜 고르기)를 앞에 두는 지금 흐름과, 하트로 먼저 담고 나중에 저장 목록에서 날짜로 나누는 흐름 중 어느 쪽이 P 여행자와 보통 여행자에게 맞는가. 날짜 정리 자체가 필요한가.

## 비교할 흐름 (시뮬레이터에게는 X·Y·Z로 섞어 보인다)

- **A 지금 앱**: 기준 시트 `언제: 지금 / 내일 / 날짜 고르기`. 하트는 그때 고른 날짜에 담긴다. 고른 날 기준으로 장날·철 표시가 바뀐다. 저장 목록은 날짜 구역, 줄마다 위로/아래로/다른 날로/빼기.
- **B 담고 나중에 나누기**: 날짜 고르기 없음. 둘러보기는 늘 오늘 기준(장날·철도 오늘). 하트는 날짜 없이 담긴다. 저장 목록에서 원할 때만 줄을 「날짜에 두기」로 나눌 수 있고, 날짜에 둔 줄은 그날 장날·철을 보인다. 순서 바꾸기 없음.
- **C 날짜 없음**: 날짜 고르기 없음, 하트는 날짜 없이, 저장 목록은 기준에서 가까운 순 한 줄 목록. 날짜 정리 기능 자체가 없다(대조군).

세 흐름 모두 기분 한 번 → 카드 3장 → 누르면 길찾기, 기준(내 위치·숙소·지역)은 같다.

## 상황 (사람마다 해당하는 것만)

- S1 전날 밤 누워서 내일 뭐 할지 훑어보기
- S2 현장에서 「지금 뭐 하지」
- S3 여행 며칠 전 집에서 둘러보기
- S4 동행과 상의하며 고르기
- S5 2~3일 동안 담아 둔 곳을 다시 꺼내 보기

## 측정 (사람 × 흐름 × 상황마다)

- `done`: 그 상황의 목적을 이뤘나(후보를 염두에 둠 / 지금 갈 곳을 고름)
- `taps`: 대략 탭 수
- `confusion`: 헤맨 곳이 있었나(코드)
- `bound`: 「묶인다·숙제 같다·관리해야 한다」 느낌이 들었나
- `missed`: 놓친 정보(예: 내일 장날)
- `again`: 다음에도 쓸까(1~5)
- 사람마다 세 흐름 선호 순위

## 판정 규칙 (미리 정함)

1. **B 채택(A 대신)**: P 여행자 집단에서 `done_B ≥ done_A − 2%p` 이고 `bound_B ≤ bound_A` 이고 `confusion_B ≤ confusion_A + 2%p`. 그리고 보통 여행자 집단에서 `done_B ≥ done_A − 5%p`.
2. **날짜 정리 자체를 뺄지(C)**: 1이 성립한 뒤, P 집단에서 `done_C ≥ done_B − 2%p` 이고 S5에서 `done_C ≥ done_B − 5%p`면 날짜 정리는 필요 없다고 본다. 아니면 B.
3. 1이 성립하지 않으면 지금 흐름(A)을 유지하고, A에서 가장 많이 나온 `confusion`·`bound` 코드 상위 3개를 고칠 거리로 낸다.
4. **신뢰 점검**: 50명을 서로 다른 시뮬레이터 둘이 따로 돌려 `done`·`bound` 일치율을 잰다. 80% 미만이면 결과 전체를 「낮은 신뢰」로 표시하고 판정은 참고로만 쓴다.
5. 흐름 이름(A/B/C)은 시뮬레이터에게 숨기고 사람마다 순서를 섞는다.

## 한계 (미리 적음)

가상 인물은 실제 사용자가 아니다. 결과는 가설이고, 실제 판단은 자체 사용 기록(날짜 모드·하트·저장 목록 사용)과 실제 사용자 반응으로 다시 확인해야 한다. 페르소나는 커뮤니티·통계 조사에 근거를 두되, 조사로 확인 못 한 비율은 「추정」으로 적는다.

## 수정 1 (2026-10-08, 결과 보기 전 — 선행 연구 13-research-methods.md 반영)

1. **로그 재생(R5)**: 시뮬레이터는 상황마다 「누른 순서」(행동 어휘, `sim/engine.mjs`)와 짧은 이유만 낸다. `taps`·`done`·막힘(`invalid`)은 엔진이 재생해 센다. `done` 규칙은 `engine.mjs judge()`로 고정: S1·S3 = 하트 1개 이상 또는 길찾기, S2·S4 = 길찾기, S5 = 저장 목록에서 이전에 담은 곳으로 길찾기.
2. **두 라운드**: 라운드 1 = 사람마다 첫 상황 하나(S1~S4, `sample.mjs firstScenario`). 엔진이 그 결과로 저장 목록 화면을 그려(`renderSaved`) 라운드 2 프롬프트에 넣는다. 라운드 2 = 저장한 곳이 있으면 S5(S1 뒤면 다음 날, S3 뒤면 3일 뒤 첫 날), 없으면 S2.
3. **흐름 분리(R6)**: 한 시뮬레이터 호출은 흐름 하나만 본다. 선호 순위는 200명 층화 표본에서만, 세 흐름 요약을 순서를 바꿔 두 번 묻고 다르면 「선호 불명」.
4. **모델 분리(R4·R10)**: 서사 = Sonnet, 시뮬레이션 = Opus, 교차 확인 50명 = Haiku(같은 50명·세 흐름·두 라운드). `bound` 코드는 시뮬레이터 자유 문장을 규칙 사전으로 분류하고 50건은 내가 검수한다.
5. **잡음 폭(R9)**: 본 실행과 별개로 100명 × 흐름 Y × 라운드 1을 같은 설정으로 한 번 더 돌려 `done` 일치율·비율 차이를 잰다. 차이가 2%p를 넘으면 규칙 1·2의 2%p 경계를 「판정 불가 구간」으로 표시한다.
6. **판정의 주 비교(R11)**: 같은 사람 안의 흐름 차이(짝 비교, McNemar)로 본다. P 대 보통 집단 차이의 크기는 「방향만 참고」.
7. **추가 측정**: S5에서 Y의 「지난 날 접힘」 때문에 못 찾은 경우(`invalid`에 `saved:go`)를 따로 센다. 이건 결과를 보기 전에 엔진 시험에서 발견한 구조적 위험이다(밤에 `지금` 상태로 담으면 다음 날 지난 날로 접힘).
8. **분포**: 나이·성별·나이별 동행·체류일·방문 횟수·숙소·교통·직업은 2025 실태조사 원보고서에 고정(확인). P 65% / 보통 35%, 유형 비중, 저장 습관은 추정 — R1에 따라 P 비율을 ±절반으로 재가중해 판정이 뒤집히는지 표로 낸다.
9. **흐름 설명 중립화**: X 설명의 「날짜에 안 둬도 아무 문제 없다」를 뺐다(다른 흐름엔 없는 안심 문구, R6).
