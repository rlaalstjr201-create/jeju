# 보고서 — 가상 여행자 1000명으로 본 「날짜」와 「저장」 흐름

작성 2026-10-08. 근거: `00-prereg.md`(사전등록·수정 1·2), `30-results.md`(사전등록 판정), `31-results-strict.md`(처음 엔진 판정), 조사 `10`~`13`.

## 한 줄 결론

날짜를 먼저 고르게 하는 지금 흐름은 밤에 훑어보고 다음 날 꺼내 쓰는 P의 행동과 구조적으로 어긋난다(밤에 담은 곳이 다음 날 「지난 날」로 접힌다). 하트는 날짜 없이 담고, 날짜는 저장 목록에서 원할 때만 붙이는 흐름(B)을 권한다. 다만 시뮬레이션 숫자 자체는 「낮은 신뢰」라, 흐름 선택은 조사 근거와 구조 분석이 주된 근거이고 시뮬레이션은 방향 확인이다.

## 무엇을 했나

1. **조사**: P형 여행 커뮤니티 글 885건(유형 14개), 2025 제주 방문관광객 실태조사 원보고서(내국인 7,015명), 여행 앱 저장 습관, LLM 가상 인물 선행 연구(Stanford 1000명 에이전트, UXAgent, AgentA/B, TinyTroupe, PersonaHub, 비판 연구).
2. **가상 인물 1000명**: 나이·성별·나이별 동행·체류일·방문 횟수·숙소·교통·직업은 실태조사 비율에 고정, P 650명(14유형)·보통 350명(4유형)은 추정 비율. 900명은 생활 서사(Sonnet), 100명은 서사 없는 대조군.
3. **흐름 3개**: A 지금 앱(날짜 먼저) · B 담고 나중에 날짜(선택) · C 날짜 없음. 시뮬레이터에게는 이름을 숨기고 한 호출에 한 흐름만 보였다.
4. **두 라운드**: 첫 상황(전날 밤 / 현장 / 며칠 전 집 / 동행 상의) → 엔진이 그 사람의 저장 목록을 그려 → 다음 날 다시 꺼내기. 시뮬레이터는 누른 순서만 내고, 성공·탭·막힘은 화면 엔진이 재생해 셌다(Opus 6,000회 + 잡음 측정 100 + Haiku 교차 300 + 선호 400).

## 사전등록 판정과 신뢰도

| 항목 | 결과 |
|---|---|
| 규칙 1 (B가 A를 대신) | 숫자로는 **성립**: P done 66.2 vs 60.8, 부담 3.2 vs 4.2, 헤맴 37.8 vs 48.3, 보통 57.6 vs 52.1. 처음 엔진으로도 성립 |
| 규칙 2 (날짜 정리 자체를 빼기, C) | 숫자로는 **성립**: P done C 66.5 vs B 66.2. 처음 엔진으로도 성립 |
| 신뢰 점검 | 같은 조건 재실행 차이 3.0%p(> 2%p) → 2%p 경계는 판정 불가 / Haiku 교차 일치 61~69%(< 80%) → **「낮은 신뢰 — 참고만」** |
| 사후 플라시보 | 화면이 같은 상황(현장·동행)에서도 A가 B보다 6%p 낮았다(p<.05). A의 전반적 열세 중 상당 부분이 시뮬레이터 잡음일 수 있다 |
| 선호 순위(두 번 일치) | P: B 28% · C 28% · A 15% · 불명 28%. 보통: C 27% · B 21% · A 16% · 불명 36%. 일정 짜는 계획형은 B·A(날짜 정리 있음)를 고르고 C는 거의 안 골랐다 |

정리하면 시뮬레이션은 「A가 B·C보다 낫다」는 근거는 주지 않고, 「B와 C 중 무엇」은 가르지 못한다.

## 잡음과 무관하게 남는 발견

1. **밤에 담은 곳이 다음 날 숨는다(지금 앱).** `지금` 상태에서 하트를 누르면 오늘 날짜로 저장된다. 자정이 지나면 그 줄은 ♥ 숫자에서 빠지고(오늘 이후만 셈) 목록 맨 아래 「지난 날」에 접힌다. 시뮬레이션에서 밤에 하트를 누른 사람 중 「내일」로 바꾸고 담은 비율은 38%뿐이었고, 다음 날 꺼내기 상황의 86%가 「♥ 0 + 접힘」 상태였다(이때 성공 43% 대 접히지 않았을 때 78%, 사람이 달라 크기는 부풀었을 수 있음). 구조 자체는 코드로 확인된다.
2. **P가 싫어하는 건 후보가 아니라 확정이다.** 커뮤니티 근거: 저장은 「메뉴」이지 일정이 아니다, 다 못 가는 걸 받아들인다, 묶인다고 느끼는 건 시간·순서·날짜 확정, 목록이 관리 대상이 되면 다시 부담(`10-research-p-archetypes.md`). 시뮬레이션 부담 코드도 날짜 정하기(A 57건, B 54건)와 목록 관리가 많았다.
3. **계획형에게는 날짜 정리가 필요하다.** 보통 집단 안에서 C(정리 기능 없음)의 부담이 B보다 높았고(11.1% 대 7.0%, 짝 비교 p<.01), 계획형은 선호에서 C를 거의 고르지 않았다. 날짜 정리를 아예 없애면 동행 중 계획을 맡은 사람이 불편해진다.
4. **흐름과 상관없이 반복된 마찰**(모든 흐름·모든 모델에서 나옴): 카드에 운영시간·휴무·평점이 없어 지도 앱에서 다시 확인 / 「다른 3곳 보기」가 화면 아래라 못 봄 / 버스·택시 이용자에게 「차로 약 N분」만 보임 / 밤·집에서 본 「오늘 장날·비 소식」이 내일 얘기인지 헷갈림 / 하트를 누르려다 카드를 눌러 길찾기가 바로 열림.

## 제안하는 UX 흐름 (B를 바탕으로)

**첫 화면·카드: 그대로.** 기분 한 번 → 3장 → 누르면 길찾기. 둘러보기는 늘 「지금」 기준이다. 기준 시트의 `언제: 지금 / 내일 / 날짜 고르기` 줄은 뺀다(시트가 짧아지고 「어디」가 먼저 보인다).

**하트: 날짜 없이 담는다.** 담는 순간 아무것도 정하지 않는다. 담은 곳은 지울 때까지 사라지지 않고 접히지 않는다(밤에 담고 다음 날 꺼내는 흐름이 끊기지 않게).

**저장 목록(♥ N): 메뉴처럼.**
- 맨 위 「담아 둔 곳」 — 날짜 없는 곳, 지금 기준에서 가까운 순. ♥ N은 이 묶음까지 센다.
- 줄마다 `날짜에 두기`(오늘 / 내일 / 날짜 고르기) — 선택. 날짜에 둔 곳은 그 날짜 묶음으로 가고, 그날 장날·철이면 그 글자가 붙는다(전날 밤에 「내일 장날」을 보는 길은 여기다).
- 순서 바꾸기·시간·메모는 넣지 않는다(확정의 도구라 P에게 부담, 계획형은 날짜 묶음으로 충분).
- 날짜에 둔 날이 지나면 그 곳은 「담아 둔 곳」으로 돌아온다(접어서 숨기지 않는다).

**함께 볼 것(흐름 결정과 별개, 근거는 위 4번):** 카드의 「다른 3곳 보기」 위치, 대중교통 이용자의 이동 문구, 밤·제주 밖에서 오늘 판의 「오늘」 표기. 운영시간·평점은 ADR-0027·카드 원칙과 부딪히므로 넣자는 제안이 아니라 「사람들이 거기서 지도 앱으로 나간다」는 관찰으로만 남긴다.

## 실제 데이터로 먼저 확인할 것 (R12)

시뮬레이션은 가설이다. 바꾸기 전에 자체 사용 기록(`/api/events`, GA4)에서 본다:
1. 하트 중 날짜를 고른 상태(`dated`)에서 누른 비율 — 날짜 고르기를 실제로 쓰는가
2. 밤(20시 이후)에 누른 하트가 다음 날 저장 목록 열기·길찾기로 이어진 비율 — 「지난 날 접힘」이 실제로 끊는가
3. 저장 목록의 위로/아래로/다른 날로 사용 횟수

## 한계

- LLM 가상 인물은 실제 사람이 아니다. 개인 행동 재현 정확도는 낮고(선행 연구 약 12%), 분산은 작게, 집단 차이는 크게(2~4배) 그리는 경향이 있다.
- 신뢰 점검 둘 다 사전등록 기준에 못 미쳤다(재실행 3.0%p, 교차 모델 61~69%).
- 처음 엔진은 「시트를 고르면 닫힌다」를 시뮬레이터에게 알리지 않아 막힘 359건을 잘못 셌다 → 결과를 보기 전에 세 흐름 똑같이 관대한 규칙으로 고쳤고(수정 2), 처음 엔진 판정도 같았다.
- 저장 목록의 장소 이름이 내부 번호(예: `walk-카드12`)로 보여, 다음 날 꺼내기 성공률의 절대값은 실제보다 낮을 수 있다(세 흐름 같은 조건).
- 표본 추출기가 상황 제약을 동행과 무관하게 붙여(혼자 온 사람에게 「아이를 챙기느라」 등) 서사 작성자가 가까운 상황으로 풀어 썼다.
- 병렬 시뮬레이터가 공용 임시 폴더에서 파일을 덮어쓴 일이 있었다. 출력 6,000줄 전부 입력과 id·상황·흐름이 일치했고, 이유 문장과 인물 속성의 모순은 3,000줄 중 1줄이었다.
- 조사 하위 작업은 웹 호출이 5회로 묶여 커뮤니티 근거 다수가 검색 요약문 수준이다. P 비율·유형 비중·저장 습관 비율은 추정이다.
