# 라이트하우스 전·후 — 자동 지역 기본 켬 (U19, 2026-10-30, 측정 전 고정)

근거: `plans/nationwide-app.md` U19, ADR-0100(「느려졌는지는 Lighthouse로 다시 재야 한다」), `specs/home-v2.md` 47(전후 한 번씩, 숫자 기준 없이 남기고 나빠진 값을 숨기지 않는다). 이 절차는 재기 전에 커밋하고, 결과를 보고 바꾸지 않는다.

## 방법

- 도구: Lighthouse CLI 13.5.0(npx 캐시에 있던 것, 새로 받지 않음), 기본 모바일 설정(느린 4G 흉내, CPU 4배 느림), `--chrome-flags="--headless=new"`.
- 쪽: 앱 홈 `/` 하나. 저장소가 빈 첫 방문이라 두 쪽 모두 시작 화면이 덮인 홈이다.
- **전**: 운영 `https://yeochana.com/`(지금 배포, 부산만 켠 빌드) 1번.
- **후**: `SITE_URL=https://yeochana.com npm run build`(자동 지역 켬) 뒤 `npx vite preview --port 4395`의 `http://localhost:4395/` 1번.
- 각 1번으로 끝이다. 좋은 값이 나올 때까지 다시 재지 않는다. 실패하면 그 사실을 적는다.

## 비교할 것

- 점수: 성능·접근성·권장 사항·SEO.
- 수치: LCP·CLS·TBT·FCP·SI, 내려받은 JS 바이트(`resource-summary`의 script).
- 나빠짐 표시: 점수 2점 넘게 떨어짐, LCP·TBT 10% 넘게 늘어남. 표시만 하고 원인을 진단 항목으로 적는다(되돌리거나 다시 재지 않음).

## 해석의 한계 (미리 적음)

- 전은 Cloudflare(CDN·brotli·`_headers` 캐시 줄), 후는 로컬 `vite preview`(압축 없음, `_headers` 적용 안 됨)다. 전송 바이트와 네트워크 시간은 같은 조건이 아니다. 라이트하우스의 느린 4G는 흉내(simulate)라 실제 왕복은 반영되지 않는다.
- 후의 빌드는 이 기기의 분석 설정으로 만든다. 분석 스크립트(GA4·네이버)는 양쪽 모두 인터넷에서 받는다.
- 한 번씩이라 홈 성능은 흔들린다(2026-10-05 기록: 88~99). 작은 차이는 차이로 읽지 않는다.
