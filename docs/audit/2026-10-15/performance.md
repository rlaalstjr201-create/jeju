# 출시 전 점검 — 렉 (2026-10-15)

기준: `criteria.md` 2절. 운영 https://yeochana.com 을 Playwright로 한 번 쟀다(동작마다 5번, 중앙값). 원자료는 `performance.json`.

## 결론

**6개 중 4개 통과, 2개 미달.** 「기준 시트 열기」(중앙값 224ms)와 「첫 화면 우리 쪽 긴 작업」(중앙값 5개, 기준 0~1개)이 미달이다. 「기분 누름」은 200ms로 기준선에 딱 걸려 통과했다.

| 항목 | 기준 | 5번 값 (rest·walk·new·food·any 방문) | 중앙값 | 판정 |
|---|---|---|---|---|
| 기분 누름 → 카드 3장 | ≤200ms | 312·200·168·224·128 | **200ms** | 통과(경계) |
| 「다른 3곳 보기」 → 새 3장 | ≤200ms | 128·112·128·120·96 | **120ms** | 통과 |
| 하트 → 눌림 표시 | ≤200ms | 72·48·64·64·64 | **64ms** | 통과 |
| 기준 시트 열기 | ≤200ms | 248·192·232·224·200 | **224ms** | **미달** |
| 「다른 3곳 보기」 30번 뒤 | DOM ≤1.5배, 힙 증가 ≤5MB | 요소 301→301(1.00배), CDP 노드 598→601(1.005배), 힙 +0.46MB | — | 통과 |
| 첫 화면 우리 쪽 긴 작업(>50ms) | 0~1개 | 5·5·4·5·5 | **5개** | **미달** |

- 값은 Event Timing의 상호작용 지속시간(INP와 같은 정의, 브라우저가 8ms 단위로 반올림)이다. 20번 모두 카드·눌림·시트가 클릭 처리 안에서 DOM에 들어간 것을 확인했으므로 규칙대로 이 값을 썼다.
- 기분 누름은 다섯 중 둘(rest 312, food 224)이 200을 넘는다. rest의 312는 클릭 처리가 157ms에 끝났는데 화면에 나오기까지 155ms가 더 걸린 경우다(나머지 넷은 36~47ms). 메인 스레드 밖(합성·GPU) 지연이고 원인은 확인하지 못했다.
- 첫 화면 긴 작업은 셈법을 바꿔도 미달이다. Long Tasks API만 세면 3·3·2·3·3(중앙값 3), 아래 「첫 렌더링」을 빼면 4·4·3·4·4(중앙값 4).

## 어떻게 쟀나

- 주소: `https://yeochana.com/?area=aewol&reach=drive30`(애월 기준, GPS 없음). 운영 번들 `index-Pqr93rcy.js`는 HEAD에서 `8ebc596`(숙소 링크)만 빠진 것이고, 렌더·고르기 코드(`render.ts`·`pick.ts`·`data.ts`·`home.ts`)는 같다.
- 브라우저: Chrome 155 헤드리스. playwright-core 1.61은 `tests/e2e/browser.e2e.mjs`처럼 전역 설치본을 썼다(저장소엔 의존성이 없다). 375×812, DPR 2, 터치, 안드로이드 크롬 UA, CDP `Emulation.setCPUThrottlingRate` 4. 같은 페이지에서 계산 루프로 잰 실제 감속은 3.2~4.6배(중앙값 3.9배)다. GPU는 인텔 내장(ANGLE D3D11). 서비스워커는 막았다. 네트워크는 스로틀 없이 실제 회선을 썼다.
- 방문 5번, 방문마다 기분 하나(rest·walk·new·food·any). 첫 화면이 안정되면(데이터·사진 끝 + 2.5초) 기분 → 「다른 3곳 보기」 → 첫 카드 하트 → 기준 버튼 순으로 한 번씩 눌렀다. 사이마다 사진 끝 + 1.5초를 쉬었다. 탭은 요소 가운데에 CDP 터치(`page.touchscreen.tap`)로 했고, 재는 동안 Playwright 대기·폴링은 쓰지 않았다.
- 30번: food 한 방문. 첫 결과 화면에서 GC를 두 번 돌린 뒤 기준값을 잡고, 30번 뒤 같은 방식으로 다시 쟀다. 쓴 것은 CDP `Performance.getMetrics`·`Memory.getDOMCounters`와 문서 요소 수다.
- 긴 작업: 로드부터 첫 탭 직전까지 잰다. Long Tasks API에 LoAF(long-animation-frame) 스크립트 출처를 붙여 우리 것과 제3자를 가른다. 스모크 실행에서 Long Tasks API가 0.5초 넘는 첫 렌더링 작업을 빼먹는 것을 봤다. 그래서 본 측정 전에 규칙 하나를 더 정했다: LoAF 렌더 구간이 50ms를 넘는데 그 위에 longtask 항목이 없으면 하나로 센다.
- 관찰용(판정 밖): CDP 트레이스 방문 1번, 글꼴만 바꾼 진단 방문 1번, Node 마이크로벤치. 벤치는 운영과 같은 `spots.json`(sha256 `a1a9aaf6b5…`)으로 했다.
- **기록 끄기:** 컨텍스트 `storageState`로 로드 전에 `localStorage jeju.track=false`를 넣었다. 다음으로 확인했다: 저장 화면 버튼이 「기록 켜기」, `gtag`·`wcs` 없음, `/api/events`·`/api/feedback`·GA·네이버 요청 0건(요청 기록이 있는 6방문 기준). 그 위에 CDP로 이 주소들과 Cloudflare Web Analytics 보고(`/cdn-cgi/rum`)를 막았다. 비콘 스크립트는 그대로 두어 실제 첫 방문 비용에 넣었고, 보고는 요청 기록이 있는 6방문에서 모두 1건씩 막혔다.
- **한 번만:** 본 측정은 1회(8방문)다. 그 전에 스크립트를 점검하려고 스모크를 1회(3방문) 돌렸고, 그 수치는 쓰지 않았다. 스모크 때는 `/cdn-cgi/rum`을 아직 막지 않아서 Cloudflare 통계에 3방문이 잡혔을 수 있다.

## 원인 — 잰 숫자에 묶어서

「LoAF」 숫자는 판정에 쓴 5방문의 중앙값이다. 「트레이스」 숫자는 관찰용 방문 한 번(walk)의 값이고, 트레이스를 켠 만큼 조금 느리다.

1. **시트 열기(미달)는 클릭 안에서 강제되는 스타일·레이아웃이 대부분이다.** 클릭 처리 157ms 중 138ms(중앙값, LoAF `forcedStyleAndLayoutDuration`, 88%)가 강제 스타일·레이아웃이다. 트레이스로 보면 스타일 재계산 79ms(그 안에 글꼴 파일 로딩 19ms)와 레이아웃 50ms다. 코드 흐름(`render.ts` `renderSheet`):
   - `#app`에 `inert`를 단다.
   - `buildSheet`가 언제·어디·얼마나·날씨에 지역 15곳까지 시트 전체를 새로 만든다.
   - `hidden`을 푼다. 그러면 `html:has(#sheet:not([hidden]))` 규칙이 걸려 html이 `overflow:hidden`이 된다.
   - `focusSheet()`의 `focus()`가 그 자리에서 스타일·레이아웃을 강제한다.

   셋(`inert` 하위 트리 재계산, `:has`, 새 노드 수) 중 무엇이 가장 큰지는 갈라 재지 않았다(의심). 탭부터 시트가 다 올라오기까지는 430ms(중앙값)이고, 240ms `rise` 애니메이션이 여기 포함된다.
2. **기분 누름(경계)도 같은 꼴이다.** 클릭 처리 129ms 중 92ms가 강제 스타일·레이아웃이다(LoAF 중앙값). 트레이스로 보면 강제 레이아웃이 2번(7ms + 85ms), 강제 스타일이 3번(합 14ms)이다.
   - 1번째(7ms): 결과 화면으로 바뀌는 첫 렌더 안. 코드로 보면 `scrollTo(0)`·`crumb.focus()`가 후보다.
   - 2번째(85ms): 카드를 넣은 뒤. 코드로 보면 `reveal()`의 `getBoundingClientRect`가 후보다.
   - 어느 호출이 강제했는지는 트레이스에 스택이 없어 코드로 짚은 것이다.

   큰 쪽(85ms)은 카드 3장 레이아웃 자체라서, 강제되지 않아도 그 프레임에 할 일이다. 두 번 강제되어 더 드는 레이아웃은 7ms 정도다. 기분 한 번에 `render()`가 3번(mood·request·resolved) 도는 것은 코드에서 본 것이다. 고르기 계산 `pickCards`는 Node에서 0.2~2ms(4배로 어림잡아 1~8ms)라 원인이 아니다.
3. **「다른 3곳 보기」(통과):** 처리 71ms 중 강제분이 33ms다. 트레이스로 보면 강제 레이아웃 2번(4ms + 32ms)이다. 30번 연속 눌러도 중앙값 88ms, 최대 144ms로, 누를수록 느려지지 않는다.
4. **첫 화면 긴 작업(미달)은 방문당 5개다.** 길이는 모두 5방문 중앙값이다.
   - **첫 렌더링 654ms**(518~734). 트레이스에서 이 작업 545ms 중 440ms가 글꼴 파일 로딩(`FontDataManager`, 파일 4개)이다. 글꼴 스택 맨 앞에 맑은 고딕을 넣은 진단 방문에서는 187ms였다. 대부분 이 Windows 측정 환경의 글꼴 탓이고, 휴대폰에서는 훨씬 짧을 것이다(의심: 휴대폰에서 재지 않았다).
   - **번들 평가 113ms**(95~125). `index-Pqr93rcy.js` 모듈 실행으로, `mountApp`·첫 `render`·딥링크 적용이 여기 든다.
   - **spots.json 본문·JSON 59ms**(54~88, 5방문 중 4방문). `Response.json()` 안에서 생긴다. Node의 `JSON.parse`만 보면 3.3ms(스로틀 없음, 4배 어림 13ms)라 나머지는 UTF-8 해독·문자열 변환으로 보인다(의심).
   - **spots 처리 127ms**(113~230). `normalizeSpots`(Node 4~6ms)·홈 계산(`moodExamples`×4·`otherAreas`·`openMarkets`·`sunsetSpots`, Node 합 3~7ms)·홈 DOM(사진 22장 등)이 한 번에 돈다. 순수 계산은 4배로 어림잡아 30~50ms다. 나머지 60~200ms는 DOM 만들기·GC로 보인다(의심: 함수 단위로 재지 않았다).
   - **spots 뒤 렌더링 77ms**(68~143). 트레이스로 보면 그중 레이아웃이 63ms다.
   - **제3자:** Cloudflare 비콘 스크립트가 방문당 21~46ms였고, 그 자체로 긴 작업은 없었다. GA4·네이버는 기록 끄기라 불러오지 않았다(이번 측정에 없다).
5. **렌더 전략:** dispatch마다 `render()` 전체가 돌지만, 결과·저장·시트·홈은 서명(sig)이 같으면 건너뛴다. 30번 동안 요소 수·리스너 수가 그대로여서, 다시 그릴 때마다 쌓이는 것은 없다(측정).
6. **이미지:** 첫 화면 사진은 22장(기분 줄 48px 8장 + 다른 동네 109px 14장, 뒤 14장은 `lazy`지만 화면 가까이라 모두 받는다)이다. 방문 한 번에 받은 사진은 카드까지 21~25장, 1.1~1.3MB다. 대부분 480px webp(12~59KB)다. 기분 줄의 48px 썸네일 하나(해지개)는 480×360 PNG 468KB로, 방문마다 받은 사진 바이트의 37~42%다(데이터 `image`가 `imgpath` PNG). `decoding=async`라 메인 스레드 긴 작업으로는 잡히지 않았다. 렉보다는 휴대폰 데이터 문제다.
7. **리스너·누수:** 30번 동안 `JSEventListeners` 74→74, 요소 301→301, CDP 노드 598→601, 힙 +0.46MB다. 리스너는 mount 때 `AbortSignal`과 함께 한 번씩만 붙고, 카드 클릭은 위임으로 받는다. 누수는 보이지 않는다.
8. **스크롤·리사이즈 핸들러:** 없다. 더 보기 막대는 `IntersectionObserver` 하나로 처리하고, 탭 뒤 그 계산은 5.7ms였다(트레이스).

## 손댈 곳 (제안, 효과는 재지 않음)

- 시트: 지역 목록 같은 정적인 부분은 한 번 만들어 두고 다시 쓴다. 또는 첫 프레임 뒤에 채운다. `inert`·`focus()`가 하위 트리 전체를 다시 계산하게 하는지 먼저 갈라 잰다.
- 첫 화면: spots 도착 뒤 한 번에 하는 일(정규화 + 홈 계산 + 홈 DOM)을 둘 이상으로 나누면 긴 작업 하나가 짧아진다. 첫 렌더링은 휴대폰에서 다시 재 봐야 우리 몫을 알 수 있다.

## 측정 한계

- 데스크톱 Windows 헤드리스(인텔 GPU)라 글꼴·GPU·합성이 휴대폰과 다르다. 첫 렌더링 수치가 특히 그렇다.
- 다른 점검이 같은 기계에서 동시에 돌았을 수 있다(확인 못 함). 감속 보정값이 3.2~4.6배로 흔들린다.
- 기록 끄기 상태라 GA4·네이버가 없다. 기록을 켠 실제 첫 방문의 제3자 비용은 확인하지 못했다.
- 방문마다 기분이 달라서 기분 누름 다섯 값에는 기분 차이가 섞여 있다(기분별 값은 위 표).
- 곁가지: Cloudflare Web Analytics 비콘이 기록 끄기와 상관없이 붙는 문제는 `build-lighthouse.md`에서 이미 다뤘다. 이 측정에서는 보고만 막았다.
