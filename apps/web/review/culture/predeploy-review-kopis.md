# KOPIS 공연 갈래 (ADR-0113) — 배포 전 독립 리뷰

범위: `git diff 63e6df79..HEAD -- apps/web/functions apps/web/src apps/web/tests apps/web/public/privacy*.html apps/web/scripts/kopis-*.ts`. 읽기 전용, 2026-11-04.
확인한 것: `npx vitest run tests/kopis.test.ts tests/culture-fn.test.ts tests/culture.test.ts` 33 통과, `npm run test:nation -- tests/culture-app.test.ts` 9 통과, `npx tsc --noEmit -p .` exit 0. 실제 Cloudflare·KOPIS 호출은 하지 않았다.

결론: 하위 요청 예산, 키 보호, XSS, 출처 줄, 개인정보 안내, 제주·부산 회귀에는 문제가 없다. 막아야 할 것은 하나다. 공연 상세 묶음 주소가 공개돼 있어서, 누구나 KOPIS 호출을 마음대로 일으킬 수 있다.

## MAJOR

### M1. 공개 주소 `&shows=PF…`로 KOPIS 호출을 무제한 증폭할 수 있음 → 키 차단·기능 정지
- `functions/api/culture.ts:93-102`, `268-` (kopisChunk): 검사하는 것은 `day`가 오늘인지, id가 15개 이하인지, 형식이 `PF\d{5,8}`인지뿐이다. 오늘 날짜는 누구나 안다. id가 오늘 목록에 있는지는 보지 않는다. 존재하지 않는 id는 `parseShow`가 null을 돌려주므로 캐시에 남지 않고(실패 결과는 캐시 안 함), 다음 요청 때 또 KOPIS를 부른다.
- 시나리오: `GET /api/culture?city=seoul&day=2026-11-04&shows=PF000001,…,PF000015`를 id만 바꿔 가며 반복한다. 요청 한 번에 KOPIS 상세 호출이 최대 15번 일어나고, 표에 없는 공연장이 있으면 더 늘어난다. 속도 조절(`lastKopis`)은 isolate(작업 단위) 안에서만 먹히므로, 병렬로 보내면 isolate마다 초당 2건씩 더해진다. 실측대로라면 45~200번 호출 뒤 KOPIS가 막히고, 계속 두드리면 풀리지 않는다. 결국 공연 갈래가 하루 내내 사라지고, KOPIS가 키를 남용으로 정지할 위험도 생긴다. `&shows=list`도 KOPIS 목록 호출이 실패하는 동안에는 캐시가 안 돼(`failFor` 0) 요청마다 최대 5번 KOPIS를 부른다.
- 수정 제안(둘 중 하나):
  (a) 묶음 요청 id가 모두 엣지에 있는 그날 목록(`kopis/{day}/list`)에 들어 있을 때만 받는다. 캐시 확인이 1건 늘어 하위 요청은 45+3+1=49개로 한도 안이다.
  (b) 자기 호출에만 비밀 헤더를 붙인다. 예를 들어 `KOPIS_API_KEY`와 day로 만든 HMAC을 `X-Culture-Self`에 넣고, 헤더가 없으면 400을 준다. 이렇게 하면 `&page=`와 `&shows=list`도 함께 막을 수 있다.

## MINOR

### m1. 그날 KOPIS 목록이 빈 XML이면 자정까지 공연 없음으로 굳음
- `functions/api/culture.ts:253-261`: KOPIS가 200과 XML 헤더로 레코드 0건을 주면 `{ids:[]}`가 200으로 KST 자정까지 캐시된다. 그러면 `kopisDay`가 `ok:true`로 빈 결과를 돌려주고(L192 부근), 합친 목록도 자정까지 남는다. 원인은 일시적 장애, 키·한도 문제 같은 XML 오류일 수 있는데, KOPIS 오류 응답이 어떤 꼴인지는 확인하지 못했다.
- 시나리오: 아침에 한 번 빈 응답이 오면, 그 엣지 위치에서는 그날 공연이 하나도 보이지 않는다.
- 수정: 서울에는 매일 공연이 약 200건 있으므로, 0건이면 실패(204, 캐시 안 함)로 다루거나 `KOPIS_FAIL_S`만 캐시한다.
- 참고: 상세 7일 캐시는 이 문제에서 안전하다. 차단 HTML은 `<?xml` 검사에서 걸러지고, 오류 XML은 `mt20id`가 없어 `parseShow`가 null을 돌려주므로 캐시되지 않는다.

### m2. 첫 요청은 늘 15초를 넘김. KOPIS가 응답 없이 늘어지면 서울 목록까지 늦게 나옴
- `functions/api/culture.ts:38,174`: `wholeDay`는 KOPIS 작업이 끝나야 응답한다. 예산 20초에 진행 중인 묶음(최대 15건 × 0.5초 + 응답 시간)까지 더하면 그날 엣지 위치의 처음 몇 요청은 약 25초가 걸린다. 앱은 15초에 포기한다(`src/culture-view.ts:36`). 이 점은 ADR Consequences에 적혀 있다.
- ADR에 없는 경우는 KOPIS가 차단 대신 응답을 늦출 때다. 이때는 `kopisGet`의 8초 타임아웃이 묶음마다 걸려 매 요청이 20초를 넘는다. 일부 실패로 끝나면 합친 목록이 10분만 남기 때문에, 10분마다 처음 묻는 사람은 서울 목록조차 못 받고 5분 뒤 재시도 때에야 받는다. 「KOPIS 실패 → 서울 목록만」(ADR 5)이 이 경우에는 지켜지지 않는다.
- 수정: `wholeDay`에서 `kopis`를 약 10초(앱 15초보다 짧게)와 경주시킨다. 늦으면 그때까지 받은 것으로 응답하고 10분 TTL을 붙인다. 남은 묶음은 `waitUntil`로 계속 돌려 상세 캐시를 채운다.

### m3. 같은 제목 걸러내기가 묶음(10건) 안에서만 됨 → 품질 04 측정과 배포 동작이 다름
- `functions/_lib/kopis.ts:119`(`seen`은 `kopisItems` 호출마다 새로 만듦), `:145`(`mergeCulture`는 서울 목록과의 겹침만 봄), `culture.ts:217`(묶음 결과를 그냥 이어 붙임).
- 시나리오: 같은 제목이 두 공연장에 따로 등록돼 서로 다른 묶음에 들어가면 둘 다 남는다. 장소가 다르면 `pickCulture`의 「같은 장소 하나」에도 걸리지 않아 목록 6개에 같은 제목이 두 번 나온다. 품질 04는 `kopisItems`를 전체 공연에 한 번에 돌렸으므로(scripts/kopis-today.ts) 이 경우를 재지 않았다. ADR 3이 말하는 「같은 제목」 규칙과도 맞지 않는다.
- 수정: `kopisDay`에서 정렬한 뒤 `normTitle`로 한 번 더 걸러 내거나, `mergeCulture` 안에서 공연끼리도 걸러 낸다.

### m4. 표에 없는 공연장 좌표를 캐시하지 않음 → 날이 갈수록 KOPIS 호출이 늘어남
- `functions/api/culture.ts:290-300`: `prfplc` 응답을 캐시하지 않는다. 공연장 표는 11-04 기준 152곳이다. 새 공연장이 생길수록 목록을 다시 만들 때마다(엣지 위치마다 매일, 일부 실패 중에는 10분마다) 묶음당 최대 3건, 21개 묶음이면 최대 63건이 더 나간다. 이 호출들도 같은 속도 조절을 거치므로 차단이 빨라지고 상세 채우기는 느려진다.
- 수정: 좌표를 공연 상세 캐시 항목에 함께 넣는다(하위 요청이 늘지 않음). 별도 캐시를 쓰면 공연장 하나에 확인·저장 2건이 붙어 48+6으로 50을 넘으니, 그 경우 `CHUNK_MAX`를 낮춰야 한다. 아울러 공연장 표를 주기적으로 다시 만드는 일을 체크리스트에 넣는다.

### m5. 동시 요청이 겹쳐 KOPIS 속도가 배로 늘어남
- `culture.ts:230` `lastKopis`: 한 isolate 안에서 동시에 도는 두 묶음이 같은 `lastKopis`로 대기 시간을 계산하면 같은 순간에 함께 호출한다. 또 `cached()`는 같은 키로 동시에 들어온 요청을 하나로 합치지 않는다. 그래서 엣지 위치의 첫 25초 안에 들어온 사용자 N명이 저마다 `wholeDay`를 시작하고, 상세 캐시가 차기 전 KOPIS 호출 속도가 N × 초당 4건이 된다.
- 수정: 대기 시간을 계산한 직후 `lastKopis = max(now, lastKopis) + GAP`처럼 미리 예약한다. 겹치는 빌드는 m2의 짧은 응답과 `KOPIS_FAIL_S`로 줄인다.

### m6. 늘 실패하는 id 하나가 있으면 하루 내내 10분 캐시
- `culture.ts:217`, `kopisChunk`의 `failed`: 목록에는 있는데 상세가 빈 XML인 id가 하나라도 있으면 `failed>0 → ok=false`가 되고, 합친 목록은 자정까지가 아니라 10분마다 다시 만들어진다. 상세가 캐시돼 있어 비용은 작지만 m2·m5와 겹친다.
- 수정: 차단(null)만 실패로 세고, XML은 왔는데 공연이 없는 경우는 실패로 세지 않는다.

### m7. 상세 7일 캐시에 기간 연장·회차 변경이 늦게 반영됨
- `culture.ts`의 `SHOW_KEEP_S`: 공연 기간이 연장되면 캐시에 남은 이전 `to` 때문에 오늘 목록에 있는데도 `not-today`로 빠진다. 회차가 바뀌어도 최대 7일 동안 예전 시각이 보인다.
- 수정: 캐시한 `to`가 오늘보다 앞이면 다시 묻는다. 또는 그날 목록 XML에 들어 있는 `prfpdto`로 덮어쓴다.

### m8. 아동 공연 거르기의 빈틈과 오탐
- `functions/_lib/kopis.ts:105`: 「가족」은 성인 연극 제목(예: 「가족이란 이름으로」)도 뺀다. 반대로 `child=N`으로 등록된 캐릭터 공연(핑크퐁·뽀로로·인형극 등)은 통과한다. `prfage`(예: 「24개월 이상」·「만 3세 이상」)는 보지 않는다.
- 수정: `prfage`의 개월 수나 만 N세(N≤7)를 아동 신호로 더한다. 「가족」은 「가족뮤지컬」처럼 장르와 붙은 경우로 좁힌다.

## 확인했고 문제 없는 것
- 하위 요청(최악): 목록 호출은 서울 페이지 P(최대 30) + KOPIS 목록 1 + 묶음 C + 캐시 2 = 50이고, 30페이지일 때 C=17×15=255건까지 받는다. 묶음 호출은 확인 15 + 상세 15 + 저장 15 + 공연장 3 = 48. 목록 호출은 확인 1 + KOPIS 5 + 저장 1 = 7. 서울 페이지가 실패하면 `told(MAX_PAGES)`로 보수적으로 잡는다.
- CPU: 묶음 하나는 상세 XML 15개를 정규식으로 읽는 정도이고, 목록 페이지는 100건×2회 훑기다. 둘 다 10ms 대비 작다(추정이며 측정하지 않음). 대기(setTimeout)는 CPU에 들어가지 않는다.
- 차단 처리: 400 HTML은 `!res.ok`에서, 200 HTML은 `<?xml` 검사에서 걸러진다. 이때 묶음은 멈추고 상세 캐시는 오염되지 않는다. KOPIS 목록이 실패하면 서울 목록만 나가고 10분 캐시된다(m2의 응답 지연 경우는 예외).
- 키: URL 쿼리에만 들어가고, 로그·헤더·응답·`X-Culture-Reason`(고정 문구)에는 나오지 않는다. fetch 예외는 버린다.
- XSS: 제목·장소·출연은 모두 `textContent`로, aria-label은 `setAttribute`로 넣는다. `link`·`image`는 DOM에 쓰이지 않는다.
- 회차 변환: 「화요일 ~ 금요일(20:00), 토요일(15:00,19:00)」은 「화-금요일 20:00 / 토요일 15:00, 19:00」이 되고 `parseCultureTime`의 GROUP으로 읽힌다(「금-월」처럼 넘어가는 범위 포함). HOL과 시각 아닌 말은 빠진다.
- 출처 줄: 보이는 고른 항목(홈 2개 또는 목록 6개)에 `kp-`가 있을 때만 붙는다. 4개 언어 모두 문구가 있다(`words()`의 Object.assign으로 덮어씀).
- 개인정보 안내 4개 언어: 서버가 KOPIS에서 받아 함께 돌려주고 위치는 보내지 않는다는 내용으로, 코드와 맞다.
- 제주·부산 등: `city!=='seoul'`은 이전과 같이 400이다. 진입 번들에는 i18n 문자열만 늘었고(언어 파일은 동적 import), `kopis-venues.json`은 functions에서만 import한다.

## 재리뷰 (9fd75a79)

범위: `git show 9fd75a79` 그리고 `functions/api/culture.ts` 전체를 다시 읽었다. 읽기 전용이며 2026-11-04에 했다. `npx vitest run tests/culture-fn.test.ts tests/kopis.test.ts`는 19개 모두 통과했고, `npx tsc --noEmit -p .`는 exit 0이었다. 실제 Cloudflare나 KOPIS는 부르지 않았고, CPU도 재지 않았다.

결론: M1은 닫혔다. 이제 바깥에서 KOPIS 호출을 일으키는 길은 맨 위 목록 요청(`?city=seoul`) 하나다. 이 요청은 엣지 캐시(Cloudflare 데이터센터별 저장본)에 막혀 있다. 남은 틈은 캐시가 비는 순간에 동시 요청이 몰리는 경우(m9)뿐이다.

### 확인했고 문제 없는 것
- 공개 경로를 다시 셌다.
  - `&shows=`: 서명을 확인하기 전에 KOPIS를 부르는 길이 없다(L101). 이 확인은 `cached()`보다 먼저 일어나므로 `shows=list`도 막힌다. 테스트(서명 없음, `x`)가 400을 확인한다.
  - `&page=`: 서울 API만 부르고 KOPIS 갈래와는 무관하다.
- 맨 위 목록 요청은 쿼리나 호스트와 상관없이 캐시 키가 `culture.cache/seoul/{day}` 하나로 고정돼 있다. 그래서 주소를 바꿔 캐시를 우회할 수 없다. 다시 만드는 주기는 데이터센터마다 다음과 같다.
  - 정상: 하루 1번(KST 자정 이후 첫 요청)
  - KOPIS 일부 실패, 예산 20초 초과, 빈 목록: 10분마다 1번
  - 서울 실패: 5분마다 1번. 이때도 `kopisDay`는 이미 출발했으므로 KOPIS 목록 1~3건은 나간다.
- 다시 만들 때 한 번에 드는 KOPIS 호출(추정):
  - 목록: 약 3건(204건이면 100+100+4), 많아야 5건. 성공하면 자정까지 캐시되고, 실패하면 캐시되지 않는다.
  - 상세: 묶음 2줄이 0.5초 간격으로 20초 동안 돈다. 진행 중인 묶음까지 합쳐 약 8~10묶음, 상세 80~100건에 공연장 조회가 묶음당 최대 3건 붙는다. 넉넉히 잡아 약 130건이다.
  - 이틀째부터는 상세가 7일 캐시돼 있으므로 목록 3건과 새 공연분만 든다.
- `*.pages.dev`: Cloudflare 문서에 따르면 Pages Functions는 `*.pages.dev`에서도 Cache API가 동작한다. `yeochana.pages.dev`는 미들웨어가 301로 넘긴다. 배포마다 생기는 `<hash>.yeochana.pages.dev`는 운영 환경변수로 함수를 돌리지만, pages.dev 쪽 캐시 공간 하나를 함께 쓴다. 그래서 데이터센터마다 하루 1번 다시 만드는 일이 한 벌 더 생길 뿐이다. 프리뷰 환경에도 `KOPIS_API_KEY`를 넣었다면 그 환경도 마찬가지다.
- Web Crypto HMAC: Workers는 `crypto.subtle.importKey` 'raw'와 HMAC/SHA-256을 지원한다. Node 테스트에서도 전역 `crypto`로 통과했다.
- CPU(추정): HMAC 한 번은 수십 µs 수준이다. 목록 호출 한 번은 서명을 1+묶음 수(최대 약 48)번 만들어도 1ms를 넘지 않는다. 묶음 호출 한 번은 1번이다. 10ms 한도에는 영향이 없다.
- 비교 타이밍: `!==`는 상수 시간 비교가 아니다. 하지만 메시지(`day|shows`)마다 다른 256비트 MAC이고 Workers의 네트워크 흔들림이 훨씬 크므로 문제 삼을 정도가 아니다. 깔끔하게 하려면 `crypto.subtle.verify`를 쓰면 되지만 고칠 필요는 없다.
- 헤더 전달: 자기 호출은 `ctx.request.url`의 호스트, 즉 이 프로젝트로 라우팅된 호스트로만 간다. 따라서 서명이 밖으로 나가지 않는다. 응답, `X-Culture-Reason`, 캐시 본문에도 서명은 없다. 서명은 그날 그 묶음 문자열에만 유효하다. 새더라도 같은 묶음(상세 캐시가 있는 id)만 다시 부를 수 있다. `URL.search` 설정은 쉼표를 인코딩하지 않으며, 인코딩하더라도 `searchParams.get`이 되돌리므로 서명 대상 문자열은 같다.
- 캐시 오염: 서명 검사가 `cached()`보다 먼저 일어난다. 캐시 키에는 헤더도 서명도 들어가지 않는다. 묶음 응답은 Cache API에 넣지 않는다. 서명 없는 요청은 400 no-store를 받으므로 엣지에 남지 않는다.
- 빈 목록을 실패로 처리하는 변경: 204를 주고 캐시하지 않는다. 그러면 `kopisDay`가 ok:false가 되고 합친 목록이 10분 남는다. 이전 m1(자정까지 빈 결과로 굳음)은 해소됐다. 대가로 10분마다 KOPIS 목록 1~3건이 다시 나가는데, 이 정도는 괜찮다. `if (!ids.length) return { items: [], ok: true }`(L206)는 이제 모든 id가 `SHOW_ID`에 걸릴 때만 탄다.

### MINOR

#### m9. 캐시가 빈 순간 동시 요청 N개 → KOPIS 호출 N배. 바깥에서 차단을 유지할 수 있는 마지막 길 (이전 m5가 공격 경로가 된 것. 이번 수정이 더 나쁘게 만들지는 않았다)
- `culture.ts:69-86` `cached()`는 같은 키로 동시에 들어온 요청을 하나로 합치지 않는다. `:102` `kopis/{day}/list`도 같다. 묶음은 호출마다 따로 isolate(실행 단위)에서 돌 수 있어 `lastKopis` 속도 조절(L240)이 서로 공유되지 않는다.
- 시나리오:
  1. KST 00:00:01에 `GET /api/culture?city=seoul`을 100개 병렬로 보낸다.
  2. 100개의 `wholeDay`가 모두 목록 캐시를 놓치고 각자 KOPIS 목록을 약 3건씩 부른다. 몇 초 안에 약 300건이 나가는데, 실측상 60건을 한꺼번에 보내면 51건이 차단됐다.
  3. 차단되면 ok:false가 되고 합친 목록은 10분 TTL이 된다.
  4. 공격자는 10분마다 다시 N개를 보낸다. 차단 중에는 다시 만들 때마다 목록 1건만 실패하고 멈추므로 N건이 나간다. 이렇게 차단이 계속 유지되고, 그날 공연 갈래가 사라진다.
- 서울 목록만 내보내는 대체 동작은 지켜진다. 그래서 피해는 공연 갈래가 빠지는 것과 키 남용으로 의심받을 위험이다. 공격하려면 자정이나 실패 뒤라는 시점을 맞춰야 하고 병렬 요청도 필요하므로 MINOR로 본다.
- 수정 제안(작은 것): `wholeDay`에서 `kopisDay`를 시작하기 전에 `culture.cache/kopis/{day}/building`을 확인한다.
  - 있으면 KOPIS 갈래를 건너뛰고 서울 목록만 600초로 낸다.
  - 없으면 `s-maxage=60`으로 저장한 뒤 진행한다.
  - 하위 요청이 2건 늘어난다. `SUBREQUESTS - 2` 계산을 `- 4`로 바꿔야 한다.
  - 같은 데이터센터 안에서 KOPIS 빌드가 분당 1번으로 묶인다. Cache API는 데이터센터 안에서 거의 바로 반영되지만 원자적이지는 않다. 그래서 같은 밀리초에 들어온 요청 몇 개는 통과할 수 있고, N이 한 자릿수로 줄어든다.
  - 이전 m5의 `lastKopis` 예약 수정과 함께 하면 좋다.
