# 양양 출하 이유 문장 전수 사실 확인 — 사전등록 (factcheck-양양-03)

등록: 2026-10-31, 확인 전 커밋. 근거: 배포 전 리뷰 3의 m-1 — 03 판정이 이유 문장을 새로 써서 출하되는 양양 이유 문장 대부분이 지금 글 그대로는 R2(사실 확인)를 받지 않았다. 이 문서는 결과를 본 뒤 바꾸지 않는다.

## 범위

- 출하 파일 `data/gangwon/spots-gangwon.json`의 `area` 양양 레코드 **171곳 전부**(keep 172곳에서 중복 등록 등불가든을 뺀 것)의 `reason`, 지금 출하된 글 그대로(`judge-양양-03/fixes-01.json`으로 이미 고친 마음이동해 포함). 앞 감사에서 확인받은 문장도 다시 본다.
- 입력: `factcheck-양양-03/input-01.json`~`input-04.json`(50·50·50·21곳, 출하 파일 순서). 곳마다 `id`·`name`·`type`·`cat3`·`lclsSystm3`·`addr`·`overview`(판정 입력과 같은 원문)·`reason`뿐이다. keep·기분·실내·근거 조각·앞 감사 결과는 없다.

## 방법 (한 번)

- 묶음마다 새 Opus 하위 에이전트 하나(모두 넷). 앞 판정·감사를 하지 않았고, 받는 것은 아래 지시와 맡은 입력 파일 하나뿐이다. 웹을 찾지 않고 다른 파일을 보지 않는다.
- 지시는 감사 R2와 같은 사실 오류 정의(`criteria-03.md` 5.1절 셋째 줄, 글자 그대로)다:
  > **이유 문장 사실 오류**: 이유 문장이 말하는 사실(무엇이 있다·보인다·판다·했다, 위치 관계, 숫자, 맛·감각·상태를 말하는 형용사) 가운데 하나라도 원문에 없거나 원문과 어긋남. 원문 낱말을 다른 말로 바꿔 쓴 것(같은 뜻)은 오류가 아니다. 말투·끝맺음은 사실이 아니다.
- 출력: `factcheck-양양-03/facts-NN.json`, 입력 순서대로 곳마다 `{ "id", "factError": true|false, "note" }`(오류면 무엇이 원문에 없거나 어긋나는지, 경계 사례면 그 까닭).
- 확인은 한 번이다. 다시 돌리지 않고, 고친 문장을 다시 확인하지 않는다.

## 결과에 따라

- 통과·실패 기준은 없다(감사가 아니라 고치기다). 오류 수와 경계 사례를 `REPORT.md`에 적는다.
- `factError: true`인 문장만 원문에 맞게 고친다: 원문에 없거나 어긋나는 부분을 빼거나 원문의 말로 바꾸고, 나머지는 그대로 둔다. 고친 문장도 이유 문장 규칙(`criteria-03.md` 2.4절, 빌드 검사)을 지킨다. 기록은 `judge-양양-03/fixes-01.json`(전후·까닭·원문 근거, `source: "factcheck-양양-03"`)이다. 이미 고친 곳이 다시 걸리면 그 줄의 `after`만 바꾼다(`before`는 판정 문장 그대로).
- 다시 판정하지 않는다. keep·기분·실내·sub는 바꾸지 않는다. 경계 사례(오류 아님)는 적기만 하고 고치지 않는다.
- 출하 파일을 다시 지어(`node scripts/curated/build.mjs gangwon 강릉,속초,춘천,양양`) 양양 레코드의 `reason`만 바뀌었는지 시험(`tests/curated-data.test.ts`)으로 확인한다.
